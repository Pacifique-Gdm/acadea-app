# Garde-fous avant un audit Production — préparation locale seulement

Ce document ne donne aucune autorisation de mutation Production. Au 10 octobre 2026, `main` est publiquement signalée comme non protégée par GitHub. Une intégration Git Vercel peut déployer automatiquement tout nouveau commit de la branche Production ; un push direct n'est donc pas un mécanisme d'approbation.

## GitHub et CI

Le workflow local `.github/workflows/preproduction-ci.yml` vérifie, sur PR vers `main` ou lancement manuel, les tests de pipeline, lint, TypeScript, unités, Functions, build Staging à configuration publique factice et règles Firestore/Storage sur émulateurs. Il n'utilise aucun secret ni aucun projet Firebase distant. Les émulateurs emploient l'ID `acadea-staging` parce que plusieurs fixtures de tests y font référence en dur ; aucun service distant n'est contacté. Son exécution GitHub reste **non vérifiée** tant qu'une PR de test n'a pas réellement produit les deux statuts `application-and-functions` et `firebase-rules`. Ne pas rendre ces statuts obligatoires avant cette vérification.

Le test d'intégration « affectation → grant Storage → upload → désactivation » effectue plusieurs opérations entre deux émulateurs. Son délai local a été porté de 5 à 30 secondes sans changer ses assertions positives ou négatives, après un PASS isolé et un timeout sous charge de la suite complète. Cette adaptation ne constitue pas une dérogation aux règles de sécurité ; tout refus d'upload attendu comme autorisé reste un échec.

Après validation des statuts, le propriétaire doit configurer une règle ciblant exclusivement `main` : PR obligatoire avec au moins une revue, résolution des conversations, statuts requis ci-dessus, interdiction des force-pushes et de la suppression, restrictions de bypass et de push direct selon le plan GitHub disponible. Vérifier ensuite avec un compte non privilégié qu'un push direct est rejeté. Les contrôles applicatifs de promotion demeurent distincts : SHA candidat, lignée fast-forward, diff Firebase, projet Vercel, 12 fonctions, `/version.json` et smoke HTTP. Aucun paramètre distant n'a été modifié ici.

## Firestore Production — opérations à autoriser séparément

Préconditions : confirmer le projet `acadea-production`, la base `(default)` et sa région, le plan de facturation, le périmètre IAM minimal du responsable, le budget et les coûts de stockage/restauration. Les rôles à vérifier séparément sont `roles/datastore.backupSchedulesAdmin` pour le calendrier, `roles/datastore.backupsViewer` pour la preuve de sauvegarde et `roles/datastore.restoreAdmin` pour la restauration ; ne pas distribuer `roles/datastore.owner` par commodité. Prévoir une fenêtre et un responsable de restauration. Ne pas copier les données personnelles dans les rapports.

1. Avec approbation, créer une sauvegarde quotidienne (exemple **non exécuté**) : `gcloud firestore backups schedules create --project=acadea-production --database='(default)' --recurrence=daily --retention=14d`. La rétention précise doit être validée selon le coût et les obligations de conservation ; la limite documentée est 14 semaines.
2. Attendre la première sauvegarde terminée ; relever son ID, état, horodatage et date d'expiration via la console Disaster Recovery ou `gcloud firestore backups list --project=acadea-production --location=europe-west1 --format='table(name,database,state)'`, puis `gcloud firestore backups describe --project=acadea-production --location=europe-west1 --backup=BACKUP_ID`. Un calendrier créé sans sauvegarde terminée ne lève pas R1.
3. Après approbation distincte, restaurer **vers une nouvelle base isolée**, jamais directement sur `(default)` ; exemple non exécuté : `gcloud firestore databases restore --project=acadea-production --source-backup=projects/acadea-production/locations/europe-west1/backups/BACKUP_ID --destination-database=acadea-recovery-test`. Vérifier dans la base restaurée, en lecture seule, les volumes par collection, les références paie ↔ dépenses ↔ audits, les années/écoles et les index. La sauvegarde contient les données et les index, mais **pas** les Security Rules ni les politiques TTL : les comparer au Git validé et les configurer séparément avant tout accès client à la base restaurée. Documenter les écarts et le temps réel de restauration.
4. Pour une récupération sélective, comparer dans la base restaurée l'état des seuls documents concernés, préparer un dry-run et une sauvegarde préalable ; toute écriture de retour dans la base active exige une nouvelle autorisation et un plan de conflit/idempotence. Aucune récupération sélective n'est testée pendant cette mission.
5. PITR peut compléter les sauvegardes pour une fenêtre allant jusqu'à sept jours, mais n'est pas rétroactif immédiatement à sept jours. Vérifier son coût de stockage et de lectures ; son activation est une mutation distincte à approuver. Il ne remplace pas la vérification d'une restauration.

R1 reste **bloquant** jusqu'à sauvegarde achevée et restauration isolée vérifiée. Aucun calendrier, PITR, export ou restore n'a été exécuté dans ce lot.

## Risques R7/R8 requalifiés sans mutation

R4 : l'arbre Functions local est passé de 13 alertes (1 critique, 4 hautes, 8 modérées) à 7 modérées après cinq correctifs transitifs de version patch. L'arbre applicatif racine est passé de 16 alertes (8 hautes, 7 modérées, 1 basse) à 7 (6 modérées, 1 basse) après cinq autres correctifs transitifs ciblés. Les versions chargées depuis `node_modules` ont été vérifiées, et non seulement les lockfiles. Ces corrections ne sont **pas** actives dans les Firebase Functions Staging ou Production tant qu'un déploiement distinct n'a pas été autorisé et vérifié. L'absence d'usage de `trust proxy` ou `req.ip` dans les Functions applicatives réduit l'exposition connue du cas `proxy-addr`, mais ne justifie pas de conserver la version vulnérable. Les alertes modérées résiduelles autour de `firebase-admin`, `@google-cloud/storage`, `gaxios`, `retry-request`, `teeny-request` et `uuid` demandent une mise à niveau coordonnée des SDK, non tentée à l'aveugle. Le `@fastify/busboy` ancien porté par l'outil de développement Vercel reste dans l'arbre de développement mais n'apparaît pas dans l'audit `--omit=dev` ; aucune conclusion de non-exploitabilité universelle n'est revendiquée.

L'avis [GHSA-jqcg-44mw-7w3h](https://github.com/advisories/GHSA-jqcg-44mw-7w3h) établit que `proxy-addr` est corrigé en `2.0.8`. Les autres versions ont été sélectionnées d'après les plages des avis npm et vérifiées avec `npm ls` après `npm ci`.

R7 : les tests locaux de l'agrégateur Coordination couvrent deux écoles USD/CDF, plusieurs écoles d'une devise et un sous-périmètre. Le code filtre les élèves, frais et paiements sur l'année active avant d'agréger par devise d'école ; les arriérés historiques sont affichés séparément selon la devise stockée sur chaque paiement. Le bundle principal observé au build local reste à environ 2,385 Mo minifiés / 681 Ko gzip et Vite signale un chargement Firebase Auth à la fois statique et dynamique. Optimisations à étudier séparément : frontières de chargement par portail, séparation des bibliothèques PDF et contrôle des imports Auth. Aucune réduction n'est démontrée dans ce lot. Un cas où la devise de l'année active diffère de `school.currency` mérite une validation de données avant de conclure à l'absence universelle de mélange ; aucun taux de change implicite ne doit être appliqué.

R8 : la consultation read-only des logs Vercel Production sur 14 jours a retrouvé **un** `POST /api/provision-school-account` HTTP 409 de niveau `error` ; les messages ne permettent pas de classer avec certitude sa cause sans données sensibles supplémentaires. Le code renvoie volontairement 409 pour des préconditions telles qu'école indisponible, téléphone déjà utilisé, conflit d'année ou de liaison parent et mise à jour concurrente. Un 409 seul ne prouve donc ni panne serverless ni réussite attendue. Le cas reste non conclu et demande une corrélation contrôlée avec l'action utilisateur et le code d'erreur public, sans création de compte Production pour reproduire.
